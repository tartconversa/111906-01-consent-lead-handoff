# 业务交付与撤回回收说明

本文说明 `handoff` 项目如何依据登记门户的授权，把咨询交给参展旅行社，以及授权变化后
如何回收。界面操作与格式边界以 [来源契约](source-contract.md) 为准。

## 角色与入口

| 角色 | 页面 | 本项目如何访问 |
| --- | --- | --- |
| 登记门户 | `/`、`/consultation/<咨询号>` | 打开列表，逐张卡片读姓名、行程、电邮、电话；点开“查看签署授权”读授权 |
| 展商 A / B 收件台 | `/receiver/A`、`/receiver/B` | 填“交付引用”并上传 JSON 名单，读历史页逐行结果 |
| 停用回执 | `/stop/A`、`/stop/B` | 填引用、原交付、咨询号、字段后提交，读 pending / confirmed |

所有交互都通过 Chromium 页面完成。项目不读取 `fixtures/`、来源内存、Python 实现，
也不直接调用表单请求。

## 咨询身份

- 咨询号（如 `L-101`）是唯一身份。同一观众可以有多次行程，同一家庭可以共用电邮，
  这些都不构成合并依据。
- 登记时记录访客号、行程和姓名仅用于展示；`record_consultation` 会拒绝同一咨询号
  出现不同身份，避免页面串号被静默合并。
- 授权抽屉中的 `A` / `B` 是获准接收的展商，列表是**该版本**获准使用的渠道
  （`email`、`phone`）。缺少展商或空列表都表示没有许可。

## 授权版本与证据

- 每次打开抽屉读到的内容以规范化 JSON 求 SHA-256，按摘要存入受限证据目录。
- 版本号变化视为新的授权证据，追加到该咨询的历史；最新版本决定当前许可能力。
- 若版本号相同但内容不同，登记会报冲突并停止；确认页面后可用 `sync --overwrite-evidence`
  明确覆盖。这样不会把一次页面异常当成授权变化。
- 业务查询只展示版本、获准字段名和证据摘要。需要核对签署原文时用
  `evidence --digest ... --reason ... --output ...`，输出写入 0600 文件并记审计，
  不回显到终端。

## 交付流程

1. `sync` 读取登记列表与所有可打开的咨询卡，并重读已登记但不在列表中的咨询号
   ——授权可能在列表之外撤回，旧页面仍可核实。
2. `prepare --vendor X` 只挑选尚未在该展商产生交付行、当前仍获许可的咨询。
   已在本次演练中接收或拒收的咨询不会自动重新组装；拒收需显式 `retry`。
3. `send` 先按同一引用查收件历史；若已存在则直接采纳，不重复上传。否则逐行重新读取
   授权，只构造目标展商获准的字段，然后通过页面表单上传。
4. 上传后立即读历史页，把每行的 `accepted` / `rejected` 写回。部分接收时交付为
   `partial`，已接收行不会被再次投递。
5. 响应丢失（`--lose-response` 或真实 503）时，行标为 `uncertain`、保留原引用；
   `send` 或 `resume` 会用同一引用重查历史页。对方若已保存，会找到并采纳回执。

交付状态：`prepared`、`delivered`、`partial`、`declined`、`uncertain`、
`nothing_to_send`。行状态：`candidate`、`accepted`、`rejected`、`withheld`、`uncertain`。

## 拒收重试

- 拒收行必须使用新的交付引用。`retry --reference REF` 会为这些行开新引用，旧引用内容
  不变，只在旧行上记录 `superseded_by`。
- 重试前会重新读取授权；已经撤回的渠道不会进入新引用。若所有被拒咨询都已无许可，
  命令会停止并提示先核对授权、执行回收。

## 授权核对与回收

`verify` 重新读取登记页面，然后按“展商 + 原交付引用 + 咨询号”比较：

- 已在该展商**实际接收**的字段（`accepted` 行的 `fields_sent`）；
- 该咨询当前授权版本允许的字段。

二者之差就是暴露范围。例如 L-101 曾把 `email` 和 `phone` 交给 A，之后授权缩小为仅
`email`，则 `phone` 属于暴露字段。`verify` 会为每段暴露登记一条停用申请，同一条交付行
只登记一次，重复执行不会重复建单。

- `requested`：已登记、尚未向展商提交。
- `pending`：已提交且回执页显示收到请求——**不代表已停用**。
- `confirmed`：回执页显示对方已停用，此时该字段才算回收完成。

`stops --submit` 提交申请并刷新回执；不带参数只刷新。`risk` 汇总所有仍暴露的字段以及
其停用状态，`action_needed` 为真的行表示尚未确认停用。回收只会发给实际接收该字段的
展商，另一家仍被授权的咨询不会出现在其停用申请里。

## 状态与隐私

`handoff-state/state.json` 保存：

- 咨询号、访客号、行程、姓名；
- 每个授权版本的版本号、采纳时间和摘要；
- 每个交付的引用、行状态、获准**字段名**、回执号；
- 每个停用申请的引用、字段名与状态。

它不保存电邮或电话原值。普通日志 `handoff.log` 同样只有标识与状态。上传名单在内存中
按需构造，上传后只保留脱敏的回执行。

证据目录建议单独挂载或备份到受限位置：

```bash
python3 -m handoff.cli --state /secure/handoff/state.json --evidence /secure/evidence sync
```

## 页面操作的可观察性

默认无头运行；加 `--headed` 可看到 Chromium 打开咨询卡、展开授权抽屉、填写收件表单、
提交停用申请的过程。所有页面读取都会等待页面加载完成，找不到预期结构时抛出
`PortalError` 并停止，而不是猜测内容。
